DV-Poll: Production build specification 1. Project overview Build DV-Poll, a Google Poll-inspired Progressive Web Application (PWA) for creating, sharing, managing, and participating in public polls. The application must be lightweight, responsive, privacy-conscious, quota-efficient, and reliable under concurrent usage. Technology stack - Frontend: HTML5, CSS3, and vanilla JavaScript. - Backend: Google Apps Script (GAS). - Database: Google Sheets. - Communication: Google Apps Script web-app endpoints using "google.script.run" where appropriate, or a correctly implemented HTTP interface where required. - Deployment: Google Apps Script web app. - Application architecture: Modular JavaScript with clearly separated responsibilities. Do not introduce frameworks, external databases, authentication providers, or paid services unless explicitly approved. 2. Mandatory architectural philosophy Event-driven communication The application must operate strictly on a user-action-triggered basis. No polling. No pinging. No heartbeat. No unnecessary background requests. Implement the following rules: 1. Loading the application must not initiate periodic backend requests. 2. Do not implement "setInterval()" for backend communication. 3. Do not use recursive "setTimeout()" calls to periodically contact GAS. 4. Do not implement heartbeat endpoints. 5. Do not send periodic requests to check whether polls, announcements, or results have changed. 6. Fetch poll information when a user opens or explicitly refreshes a poll. 7. Fetch results when a user requests results or when the selected result-visibility policy permits their display. 8. Submit votes only after an explicit user action. 9. Save poll settings only when the user submits the relevant form. 10. Perform telemetry collection only during legitimate application interactions, without introducing independent recurring requests. 11. Do not retry failed requests indefinitely. Any retry must be bounded, justified, and safe against duplicate submissions. 12. Do not prefetch every poll or load all database records when a visitor opens the application. A user action does not automatically justify a separate request if the information can be returned by an existing request. Reuse responses where practical. Do not create a backend request merely to discover whether another request is necessary. Important implementation distinction A frontend event handler is not itself a backend request. Local operations such as opening a modal, changing a theme, validating a form, copying a poll link, and displaying cached information must work without contacting GAS when backend information is unnecessary. Do not claim that the application makes zero requests on initial load if the implementation actually requests essential configuration or poll data. 3. Coordinate modules. - Manage navigation and application state. - Handle common dialogs and notifications. - Provide a centralized communication layer. - Prevent duplicate submissions caused by repeated taps. poll.js - Create polls. - Add, edit, and deactivate options. - Display poll details. - Validate voting forms. - Submit votes. - Display permitted results. - Generate shareable poll links. - Implement the specified result-visibility policies. telemetry.js - Display published announcements. - Support authorized announcement creation and editing. - Fetch announcements only when needed. - Do not implement periodic announcement refreshes. 4. Database relationships Implement these logical relationships: - "Polls" → "Options": one-to-many. - "Polls" → "Votes": one-to-many. - "Polls" → "Poll_Results": one-to-many. - "Polls" → "Analytics_Daily": one-to-many. - "Options" → "Votes": one-to-many. - "Voters" → "Votes": one-to-many. - "Voters" → "Banned_Voters": one-to-many where a voter-targeted restriction exists. - "Votes" → "IP_Telemetry": zero-or-one related telemetry record. - "Audit_Log" → relevant entities through "target_id" and event metadata. - "System_Audit": standalone operational logging. - "Maintenance_Jobs": standalone maintenance metadata. Google Sheets does not enforce foreign keys. Implement and validate these relationships in Apps Script. 6. Authoritative voting procedure Implement the following server-side flow. Step 1: Validate the request Validate: - Required fields. - Poll ID and option ID. - Poll status. - Voting window. - Option membership. - Option activation. - Selection count. - Request format and size. - Applicable identity and restriction rules. Step 2: Obtain the script lock Acquire "LockService.getScriptLock()" with a bounded wait. If the lock cannot be obtained, return a clear temporary failure. Do not silently accept an unrecorded vote. Step 3: Recheck eligibility Inside the lock: - Re-read the relevant poll state. - Recheck the voting window and poll status. - Check applicable voter restrictions. - Check duplicate-vote rules. - Check multi-selection constraints. Do not rely on eligibility checks performed only before acquiring the lock. Step 4: Record the vote Write the authoritative vote record and required related state using efficient spreadsheet operations. Do not assume multiple spreadsheet writes form an atomic transaction. If the operation fails partway through: - Record or report the failure appropriately. - Avoid falsely reporting success. - Prevent unsafe automatic retries from creating duplicate votes. - Implement reconciliation for partial writes where necessary. Always release the lock in a "finally" block. Step 5: Record security metadata Store approved, minimized security metadata. Never store a raw IP address. Do not block a valid vote merely because optional geolocation or network enrichment is unavailable. Step 6: Update derived information Update results and analytics using a documented strategy. Avoid scanning every sheet for every vote. Do not launch unbounded background work or introduce periodic polling. If results are cached, invalidate or refresh the relevant cache safely. Step 7: Return a response Return a structured result indicating success or failure. Never tell the frontend a vote succeeded unless the authoritative write has succeeded. 7. Public polling rules The application must support: - Public poll discovery where enabled. - Poll creation by authorized users. - Shareable poll URLs. - Anonymous voting. - Optional verified-email voting. - Single-selection and multiple-selection polls. - Optional randomized option ordering. - Poll opening and closing times. - Configurable result visibility. - Poll closure and archiving. - Administrative moderation. Anonymous voting limitations Do not claim that a public anonymous poll can guarantee one vote per human. Browser-generated identifiers can be reset, and IP addresses may be shared or changed. Use appropriately scoped duplicate-vote controls and transparent abuse-prevention measures. For "require_login = TRUE", require a genuine verified identity mechanism. A client-submitted email address is not proof of ownership. Do not implement a fake login system that treats a typed email address as authenticated. 8. Privacy and telemetry requirements Use the following policy as the starting point for the application, but ensure the final text matches the actual implementation. Privacy policy We use limited telemetry, including protected IP-derived identifiers where available, to deliver and maintain our services, investigate outages, prevent spam, fraud and abuse, and measure audience engagement and site usage to improve service quality. We do not store raw IP addresses in our application database. We limit data collection to defined operational and security purposes and apply appropriate retention and access controls. Where third-party services are used for telemetry enrichment, disclose the relevant processing accurately. Implementation requirements - Never persist raw IP addresses. - Never expose the IP hashing secret to the browser. - Do not treat an unsalted SHA-256 hash as sufficient protection for an IP address. - Do not collect precise location data without a defined need. - Document retention periods. - Restrict administrative access to identifiable or security-sensitive records. - Do not claim that telemetry is anonymous if persistent identifiers can be linked to individuals. - Do not collect browser fingerprints unless explicitly approved and justified. Important Apps Script limitation Do not assume a standard Apps Script web-app handler receives the visitor's IP address automatically. If IP collection is required, investigate and document a supported acquisition method before implementation. Do not introduce an external proxy or third-party service without approval. If the necessary source is unavailable, preserve the schema but leave unavailable telemetry fields empty. 9. Administration and authorization Administrative privileges must be enforced on the backend. Implement: - Poll ownership checks. - Restricted administrative operations. - Poll status changes. - Moderation actions. - Announcement management. - Settings management. - Audit records for sensitive changes. - Safe handling of expired or revoked permissions. Never trust an "isAdmin" flag, email address, or role supplied by the browser. Never expose administrative secrets in HTML, JavaScript, URLs, or public spreadsheet output. Before enabling an administrative feature, define how the administrator is authenticated and authorized in the deployed environment. 10. Announcements Announcements must: - Support creation and editing by authorized administrators. - Support publication status. - Display only published announcements to ordinary visitors. - Use safe text rendering. - Avoid automatic recurring refresh requests. - Load only when needed. If announcements are displayed on the home screen, retrieve them during the relevant initial data request or through a clearly justified user-action-triggered request. 11. Performance and quota management Implement: - Batched spreadsheet reads and writes. - Narrow, targeted data retrieval. - Cached configuration where safe. - Minimal spreadsheet scans. - Bounded lock acquisition. - Input-size limits. - Safe error handling. - Bounded retries only for operations that are safe to retry. - No redundant requests. - No automatic periodic synchronization. Do not make an individual spreadsheet API call for every cell. Do not fetch the entire spreadsheet database to render one poll. Do not perform expensive analytics recomputation synchronously for every vote if it can be safely deferred or computed on demand. Any deferred work must have a defined execution mechanism and must respect Apps Script quotas. 12. Security requirements Implement server-side validation for every mutation. Protect against: - Unauthorized administrative operations. - Duplicate vote submissions. - Formula injection. - Cross-site scripting. - Malformed identifiers. - Invalid foreign-key references. - Excessively large requests. - Invalid timestamps. - Unauthorized poll modifications. - Abuse of public endpoints. - Information disclosure through error messages. Use context-appropriate HTML escaping and safe DOM methods. Do not rely on frontend validation alone. Do not describe "LockService" as a database transaction. Do not claim that an in-memory lock protects concurrent operations across different Apps Script projects. 13. Initialization and deployment Provide a controlled database initialization function that: 1. Identifies the configured spreadsheet. 2. Creates any missing required sheets. 3. Writes the exact required headers. 4. Validates existing headers. 5. Refuses to overwrite or delete existing user data. 6. Reports schema mismatches clearly. 7. Runs only when explicitly authorized. Do not automatically reset the database when a visitor opens the application. Document: - Required Apps Script deployment settings. - Spreadsheet permissions. - Administrative authorization setup. - Any required script properties. - Any approved triggers. - Quota-sensitive operations. - Limitations of anonymous voting and IP telemetry. The application must not expose the spreadsheet ID or privileged configuration unnecessarily. 14. Testing requirements Test at least the following scenarios: 1. Opening the application causes no periodic backend traffic. 2. Opening a poll retrieves the required poll data. 3. No heartbeat requests are generated. 4. A valid vote is accepted. 5. A vote against a closed poll is rejected. 6. A vote outside the voting window is rejected. 7. An inactive option is rejected. 8. An option belonging to another poll is rejected. 9. Duplicate submissions are handled according to the defined voting policy. 10. Multiple selections obey the configured limits. 11. Concurrent submissions do not bypass server-side checks. 12. An unauthorized user cannot modify another user's poll. 13. An unauthorized user cannot perform moderation. 14. Hidden results remain hidden. 15. Formula-injection attempts are safely handled. 16. Missing optional telemetry does not invalidate a legitimate vote. 17. Failed spreadsheet writes do not produce false success messages. 18. Partial-write failures can be diagnosed and reconciled. 19. The initialization process preserves existing records. 20. All eleven sheets and their headers match the specification. 15. Acceptance criteria The build is accepted only when: - All twelve requested files are delivered. - Exactly eleven database sheets are used. - Every sheet has the specified columns. - Frontend and backend responsibilities are separated. - No periodic polling, pinging, or heartbeat exists. - User actions trigger only the backend operations they require. - Vote validation is enforced server-side. - Concurrency and partial-write failures are handled deliberately. - Anonymous voting limitations are documented. - No raw IP addresses are persisted. - Telemetry claims match the actual implementation. - Administrative functions require server-side authorization. - The application works on mobile and desktop browsers. - The installation and deployment instructions are complete. - No core functionality is represented by placeholder code. - No missing module, undefined function, or broken script dependency remains. Final instruction Build DV-Poll as a complete, integrated application. Do not simplify the architecture by removing any of the eleven database sheets. Do not silently change the specified filenames, database headers, voting policies, or privacy requirements. Where an implementation detail is technically impossible or unsupported by the selected platform, explain the limitation and provide the safest compatible implementation without pretending the requirement has been fulfilled. Deliver the complete contents of every requested file, the database initialization procedure, deployment instructions, and a concise verification report.
